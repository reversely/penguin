# Money-minor-units fixture

The money-minor-units fixture is the Git repository of Larder, the grocery marketplace in
[case-study-money.md](case-study-money.md). Fourteen people own fourteen scopes. Forty features run
as forks of main. Ines's change replaces float prices with `Money(amount_minor, currency)`, first as
one block and then as seven waves of a parallel change. Penguin's impact graph, review harness and
tests run against this repository to show case 4 of the PRD: a blocked overlapping start, a one-block
plan over the break limit, an expand wave with no place, five migrate waves, a contract wave, a
requested revision, a protected file, a running feature found midway and a late starter.

`examples/money-minor-units/build.py` builds the repository from one data file
(`examples/money-minor-units/larder.json`) plus the source directories next to it. Every build produces
the same commit SHAs. `examples/money-minor-units/pins.json` records them.

## Building

```sh
python examples/money-minor-units/build.py /tmp/larder          # one ref and SHA per line
python examples/money-minor-units/build.py /tmp/larder --pins   # the pins JSON
```

The target must be empty or missing. The builder checks all of `larder.json` first and refuses the
whole file with every problem listed. It then writes every commit through one `git fast-import`
stream, with author, committer, date and file bytes taken from the data file. A build takes under
one second on an Apple silicon laptop. The built repository holds 556 objects in a 217 KiB pack.

## The data file

`larder.json` holds every person, scope, invariant and feature. The builder generates
`penguin/owners.json`, `penguin/scopes.json`, `penguin/identities.json` and
`penguin/invariants.json` from it and commits them in the base commit, in the format the other
fixtures use. No penguin file is kept in a source directory.

| Field | Holds |
|---|---|
| `people` | The fourteen engineers: `id` and `display_name` |
| `scopes` | Each scope's `id`, `name`, `owner`, `paths`, `contracts` (`path::symbol`), `depends_on` and, for analytics, `protected_paths` |
| `invariants`, `examples` | The invariants and recorded examples written to `penguin/invariants.json`. An example with a `sample` is generated by the builder |
| `features` | Each feature's `id`, `owner`, `title`, `role`, agent name and vendor, `start` (`base` or `main`) and `commits`. A feature that declares a scope another person owns lists every scope it declares in `area`. Each wave of the parallel change is a feature with the role `wave` |
| `promotions` | Each time main moves to a feature's head: Lena's promotion stacking, then each wave in turn |
| `plan` | The one-block attempt's merge plan: the nine scopes, the kind of fix for each and the seven rewrite rules the plan declares |

Each commit names its `source` directory under `features/<feature id>/`, a `date`, a `message`, an
optional `tag` and an `author` (`owner`, `codemod` or a person). A fix commit names its `fix`: the
scope, the kind (`mechanical`, `behavioural` or `revision`) and the pytest node IDs it makes pass. A
checkpoint names in `fails_alone` the tests that fail on it before Ines's change reaches it. A commit
with `after` names the tag of an earlier commit of its feature. The builder builds it on that commit
and gives it its own tag; the feature's branch head stays where it was. Each running feature uses it
for its second fix: the one the contract wave's plan holds, beside the one-block fix at its branch
head.

Every id, path, contract, tag, test ID, name and email address is checked before anything is
written. Ids are lowercase words joined by `-`. Paths hold plain segments with no `..` and no
leading `/`. Names and email addresses hold no `<`, `>` or line break, because they go into commit
headers. `tests/test_money_fixture_builder.py` feeds hostile values such as `../money`,
`money; rm -rf /`, `/etc/` and `--force` to the loader.

wave's head. Every other branch is `feature-<id>`. A checkpoint is tagged `feature-<id>-checkpoint`.

### The waves

Each wave starts from main as the wave before left it. Every wave's checkpoint is tagged
`feature-<id>-checkpoint`.

| Wave | Area | Commits | Change |
|---|---|---|---|
| `money-type` | money, orders | `checkpoint` | `shared/money` gains `Money`, `Money.sum()` and `discounted()`; `orders/model.py` gains `line_total_minor()` and `order_total_minor()`. No existing symbol changes |
| `money-checkout` | checkout | `checkpoint`, `fix-promotions` | `cart_total()`, `charge_amount()` and `total_line()` take the cart's currency and return `Money` or its minor amount. The fix moves Lena's stacking on main to `discounted()` |
| `money-tax` | tax | `checkpoint`, `tax-per-line`, `fix-invoicing` | Tax in `Money` with `Decimal` rates, the subtotal rounded once; then Rahul's revision rounds per line. The fix moves invoicing on main to `Money` |
| `money-refunds-payouts` | refunds, payouts | `checkpoint` | Refunds and store fees in `Money`; fees round half up in the minor unit |
| `money-analytics` | analytics | `checkpoint` | Revenue per currency in `analytics/revenue_report.py`, the protected file |
| `money-messaging-mobile` | messaging, mobile-api | `checkpoint` | Receipts and order payloads read totals as `Money`; their tests are unchanged |
| `money-contract` | money | `checkpoint`, `fix-orders` | `price()`, `total()`, `display()` and `percent_off()` are removed. The fix removes `line_total()` and `order_total()` from orders on main |

`Line.unit_price` and `CartLine.unit_price` stay floats: the dollar amount an order record stores. A
Money field on `Line` would change the class, so the impact graph would list every `Line(...)` call
as a caller and the expand wave would have places. The waves read a stored price into the order's
currency with `line_total_minor()` instead. Migrated code imports `Money` by name, so removing the
float functions from `shared/money` reaches only code that still calls them.

## Expected failures and fixes

`pins.json` maps each test below to the commit that makes it pass: `fixes` for the one-block
attempt and `wave_fixes` for the waves. The slow suite (`tests/test_money_fixture_reproduction.py`)
checks every row.

- **Ines's fork.** On the checkpoint, every money test of the nine plan scopes fails, as does
  `promotions/tests/test_stacking.py`. Each step makes its own scope's tests pass. After `fix-tax`,
  `tax/tests/test_invoice.py::test_tax_rounded_per_line` and `test_invoice_tax_minor_is_in_cents`
  still fail: rounding the subtotal once turns 35 cents into 36 on a three-line order. `tax-per-line`
  makes them pass. The promotions tests fail until `fix-promotions`.
- **Readers and the midway feature.** Merged with Ines's fork, each checkpoint fails its own tests.
  Merged with Ines's fork, each fix passes.
- **The yen.** `checkout/tests/test_japan.py::test_yen_charged_at_face_value` fails on the
  `japan-launch` checkpoint alone: float main charges 150 yen times two as 30000. The fix prices yen
  lines as `Money(150, "JPY")`, so the charge is 300.
- **The late starter.** `currency-filter` imports `Money` by name from its first commit. It starts
  from main after the migrate waves, so its tests pass on the branch alone and merged with the
  contract wave.
- **The waves.** Each wave's step fails only the tests a later step of the same wave fixes. Each
  wave's head passes every scope's tests. On the tax wave's checkpoint the two per-line tax tests
  fail until `tax-per-line`. Invoicing's tests fail until `fix-invoicing`. On the contract wave's checkpoint the
  orders tests fail until `fix-orders`. The expand wave's impact report lists only added symbols.
- **Running features on the contract wave.** Merged with the contract wave, each reader's checkpoint
  fails its own tests. Merged with the contract wave, each wave fix passes.
- **Unaffected features and Hugo's rounding mode.** Each passes merged with Ines's fork. Hugo's change
  sits in `shared/money/rounding.py`, which Ines does not touch.

## Invariants and the tax sample

`penguin/invariants.json` declares 18 invariants across the fourteen scopes. Tax declares
"Tax is rounded per line item" (`tax-per-line`) and "Each order is taxed at its region's rate".
Analytics declares two protected invariants: "Daily revenue equals the sum of that day's order
totals" and "Revenue in different currencies is never added together".

Each test that `pins.json` lists under `fixes` has a one-line docstring stating what the test
protects. A merge plan states each break with that docstring. A test that checks a declared
invariant repeats the invariant's statement: `test_tax_rounded_per_line` reads "Tax is rounded per
line item." Every other test states its own rule in the same form, such as "A line's total is its
price times its quantity."

`tax/examples/invoice_tax.json` records 5,000 US orders for `tax/invoice.py::invoice_tax_minor`.
Each case passes the stored order record through `orders/model.py::Order.from_record`, so the same
input builds a float order on main and a `Money` order on the fork. The builder draws every order
from a fixed seed and keeps every draw: one to six lines, prices from 49 cents to $19.99,
quantities up to four, in one of four regions.

`examples/money-minor-units/reviews/` holds the two review forms Rahul's agent submits: one for the
whole-order tax (`tax-per-line` breaks) and one for the revision (both invariants hold). Both forms
name `Order.from_record` as the migration marker, because the contract diff shows the stored shapes
of `orders.model.Line` and `checkout.cart.CartLine` changing.

It also holds one form for each other scope a wave's plan has a part in, named after the scope, which
that scope's agent submits on the wave. `invoicing.json` is Mei's: `invoice-matches-charge` holds,
citing `invoicing/tests/test_invoice.py::test_amount_due_is_sent_in_cents` and
`invoicing/invoice.py::amount_due_cents`. `promotions.json` is Lena's:
`discount-keeps-price-positive` holds, citing `promotions/tests/test_stacking.py::test_coupons_stack`
and `promotions/coupons.py::coupon_percent`. Each cited test and definition exists on the part's
trial tree. Neither names a marker: neither scope reads a stored shape the wave changes.

## Checking the case with the bridge

Build into a directory, then run the impact graph on Ines's checkpoint against main, with each
running feature's checkpoint as a fork and the scopes its changes touch:

```sh
penguin-bridge impact --repo /tmp/larder --base feature-promotion-stacking \
  --head feature-money-minor-units-checkpoint \
  --fork japan-launch=feature-japan-launch-checkpoint:checkout ... --json
```

With the 36 running features and Noor's first checkpoint as forks, the report is complete. It
selects the 23 readers, whose scopes are the nine plan scopes, plus Hugo's `rounding-mode` fork in
`shared/money` itself. Penguin's same-area check covers that fork. It leaves out the 12 unaffected
features and Noor's first checkpoint, which touches only `shared/platform`. Noor's second checkpoint
adds `mobile_api/order_lines_page.py`. A second run selects it.

Run the tax review on the whole-order step, then on the revision:

```sh
penguin-bridge review --repo /tmp/larder --base feature-promotion-stacking \
  --fork feature-money-minor-units-fix-analytics \
  --scope tax --form examples/money-minor-units/reviews/tax-whole-order.json
penguin-bridge review --repo /tmp/larder --base feature-promotion-stacking \
  --fork feature-money-minor-units-tax-per-line \
  --scope tax --form examples/money-minor-units/reviews/tax-per-line.json
```

The first run reports `invoice_tax_minor` differing on 1633 of 5000 inputs, by one or two cents. It
raises a broken `tax-per-line` invariant for Rahul. No single-line order differs:

| Lines in the order | 1 | 2 | 3 | 4 | 5 | 6 |
|---|---|---|---|---|---|---|
| Orders differing, whole-order step | 0 | 227 | 267 | 356 | 364 | 419 |
| Orders differing, per-line revision | 0 | 2 | 1 | 1 | 0 | 6 |

The second run reports 10 of 5000 differing by one cent each, with no exception. On each of the 10
orders one line's exact tax is a half cent, all in California at 7.25%. Main's floats compute that
tax as 0.4999… of a cent and round it down. The revision rounds the exact half up, as main's
own rounding mode (`ROUND_HALF_UP`) states. The revision's tax equals exact decimal arithmetic on all
5,000 orders, so the 10 differences are float drift on main.

The tax wave gives the same counts. Its review runs against the checkout wave's head, the main the
tax wave starts from, with the same forms: `feature-money-tax-checkpoint` differs on 1633 of 5000
inputs and `feature-money-tax-tax-per-line` on 10.

## Where the fixture departs from the case study

- **Contracts.** Ines's checkpoint leaves `penguin/scopes.json` unchanged. A changed JSON file would
  make the impact report incomplete, which selects every fork. `Money` reaches the scope map by
  declaration, as [design.md](design.md#steps-1-and-2-in-the-build) describes.
- **Tax sample.** The case reports 312 of 5,000 orders differing, every one with three or more lines.
  The fixture's unfiltered sample differs on 1633, two-line orders included. The case reports no
  differences after the revision; the fixture shows the 10 orders main's floats round wrongly.
- **Fix counts.** The case counts 7 codemods and 3 agent fixes. The fixture holds 35 fix commits:

  | Fix | Where | Count |
  |---|---|---|
  | Codemod | Ines's fork: the six plan scopes and promotions | 7 |
  | Codemod | Reader forks in checkout, orders, refunds, invoicing, messaging and mobile-api | 16 |
  | Codemod | Noor's pagination fork | 1 |
  | Ines's agent, behavioural | Ines's fork: tax, payouts and analytics | 3 |
  | Ines's agent, behavioural | Reader forks in tax, payouts and analytics | 7 |
  | Ines's agent, revision | Ines's fork: tax per line | 1 |
- **Rewrite rules.** The case's codemods write exactly what the plan's rules give. The fixture's
  codemod commits were written by hand, so they also change what no rule writes. With the seven
  rules in `larder.json`, the money plan's 32 parts classify as 0 mechanical and 32 behavioural:
  the nine plan scopes on main and the 23 readers.
  The rules reproduce the code changes of 12 codemod fixes: Ines's messaging fix and the
  saved-carts, split-shipments, substitutions, partial-refunds, pdf-layout, business-accounts,
  credit-notes, order-shipped, refund-email, weekly-digest and order-history fixes. Each of those 12
  also rewrites its tests' float prices, such as `Line("milk", 2, 1.49)` to
  `Line("milk", 2, Money(149, "USD"))`. That rewrite needs a unit conversion and a currency. Its pattern
  would name `Line`, a contract outside the money change. The other 10 codemod fixes in the plan
  differ in their code too:

  | Fix | What no rule writes |
  |---|---|
  | Ines's orders, checkout, refunds and invoicing fixes; tip-jar, store-credit | Reworded docstrings; orders also reads each stored price in the record's currency |
  | Ines's mobile-api fix, cart-sync | `round(total * 100)` on a variable: no use of a money contract to match |
  | reorder | `dict[str, float]` becomes `dict[str, money.Money]` inside a parameter's annotation |
  | japan-launch | `money.price(yen)` gains the currency `"JPY"`, a choice per call |

  If every test rewrite were rule-shaped, 20 parts would stay behavioural, over the default limit of
  10. Penguin returns the plan. The preview seed leaves the returned plan in Ines's inbox.
- **Places in running features.** Every reader's fork starts at `base`, so it also carries main's
  callers in its scope, such as `checkout/cart.py` in the `japan-launch` fork. Those callers belong to
  main's part. Each reader's part lists only the callers in the module its own checkpoint adds, two
  or three per reader. Its breaks are the failing tests in its own test file, one or two per
  reader, such as `checkout/tests/test_japan.py` for `japan-launch`. The scope's tests the reader
  carries from main, such as `checkout/tests/test_cart.py`, fail on its merged tree too, but they
  belong to main's part. The plan lists 42 breaks: 18 on the nine parts for code on main and 24 on
  the 23 readers' parts. Another 46 failing tests on the readers' merged trees sit in carried files.
  The plan's `breaks` source counts them. Noor's first `pagination` checkpoint changes only `shared/platform`. The facts
  run reports its 2 callers in `mobile_api/orders.py` as carried from main, so Penguin states
  `pagination` as not affected and the plan holds no part for it. The preview seed proposes a part
  for every reader and the midway feature, then drops the part Penguin answers `not_affected`.
- **Wave counts.** The preview seed (`scripts/preview/seed.ts`) proposes each wave's plan with a part
  per fix commit the wave holds and, for the contract wave, a part per reader's wave fix. Penguin
  answers:

  | Wave | Places | Behavioural | Answer |
  |---|---|---|---|
  | `money-type` | 0 | 0 | Stored |
  | `money-checkout` | promotions | 1 | Stored |
  | `money-tax` | invoicing | 1 | Stored |
  | `money-refunds-payouts` | 0 | 0 | Stored |
  | `money-analytics` | 0 | 0 | Stored |
  | `money-messaging-mobile` | 0 | 0 | Stored |
  | `money-contract` | orders and the 23 readers | 24 | Returned |

  A migrate wave changes the code of the scopes it moves, so the running features in those scopes are
  same-area features: their people approve the wave's start, 23 approvals across the seven waves.
  Their own float calls are places only of the contract wave, which removes the functions they call.
  `apps/worker/test/money-waves.test.ts` checks each row against the larder data.
- **Noor's midway checkpoint.** The contract wave's plan is returned, so no announced plan gains a
  part when Noor's second checkpoint adds a caller. The seed reports that checkpoint only after a
  stored contract plan.
- **Routine merge conflicts.** The case resolves two import and formatting conflicts. Every fork in
  the fixture merges with Ines's fork without a conflict.
- **Agents.** The case counts about sixty agents. The fixture gives each feature one agent identity,
  47 in all with the seven waves. Each identity's charter lists its owner's scopes. A feature with an `area` in
  `larder.json` declares those scopes when it opens. Every other feature declares its owner's
  scopes.
- **Same-area forks in the impact report.** The impact graph selects Hugo's fork because it lives in
  `shared/money`. The case counts it under the overlapping start, outside the 23 readers.
- **Protected file.** `analytics/revenue_report.py` is listed in the scope's `protected_paths`. At
  the `money-analytics` checkpoint Penguin reads the wave's own change since its merge base with
  main, which is main as `money-refunds-payouts` left it. The change rewrites the protected file, so
  Jun gets one `protected_path` item for the wave with the file's diff, 38 lines with context. The
  wave's plan has no parts, so the item is the only thing the wave waits on. The preview seed has Jun
  confirm the lines once the plan is stored and before main moves to the wave's head, which signs a
  `confirm_protected_change` record on the wave. No other checkpoint the seed reports touches the
  file: Ines's one-block attempt rewrites it only in its `fix-analytics` step, past the checkpoint
  it reports, and Jun's own analytics features add files beside it.
  `apps/worker/test/money-waves.test.ts` derives the expected item from `larder.json`: each wave of
  another person whose area is a scope with `protected_paths`.

## Changing the fixture

A change to `larder.json` or to a source directory changes the SHA of every commit built after it.
Run `uv run pre-commit run --all-files` first, because ruff can rewrite a fixture source file. A new
top-level package goes into `known-first-party` in `examples/ruff.toml`, so ruff sorts its imports
