# Money-minor-units fixture

The money-minor-units fixture is the Git repository of Larder, the grocery marketplace in
[case-study-money.md](case-study-money.md). Fourteen people in four teams are DRI for 29 scopes.
Forty features run as forks of main. Ines's one feature replaces float prices with
`Money(amount_minor, currency)` by Penguin's split. Its first checkpoint is the expand. The float API
then retires and each owner's code moves over in its own block. Its last checkpoint removes the
float API once no caller is left. Penguin's impact graph, review harness and tests run against this
repository to show case 4 of the PRD: a blocked overlapping start, an expand with no place, the
retiring next step at a running feature's checkpoint, ten migration plans, a requested revision,
the contract and a late starter.

`examples/money-minor-units/build.py` builds the repository from one data file
(`examples/money-minor-units/larder.json`) plus the source directories next to it. Every build produces
the same commit SHAs. `examples/money-minor-units/pins.json` records them.

## Building

```sh
python examples/money-minor-units/build.py /tmp/larder          # one ref and SHA per line
python examples/money-minor-units/build.py /tmp/larder --pins   # the pins JSON
```

The target must be empty or missing. The builder checks all of `larder.json` first and refuses the
whole file with every problem listed. It then writes every commit through one `git fast-import`
stream, with author, committer, date and file bytes taken from the data file. A build took 0.3 seconds
on an Apple silicon laptop. After `git gc` the built repository holds 587 objects in a 237 KiB pack.

## The data file

`larder.json` holds every person, team, scope, invariant and feature. The builder generates
`penguin/owners.json`, `penguin/teams.json`, `penguin/scopes.json`, `penguin/identities.json` and
`penguin/invariants.json` from it and commits them in the base commit, in the format the other
fixtures use. No penguin file is kept in a source directory.

| Field | Holds |
|---|---|
| `people` | The fourteen engineers: `id`, `display_name` and the `vendor` their steward runs in |
| `teams` | Each team's `id`, `name`, `lead` and `members`, written to `penguin/teams.json` |
| `scopes` | Each scope's `id`, `name`, `team`, `dri`, `fallback`, `paths`, `contracts` (`path::symbol`), `depends_on` and, for analytics, `protected_paths` |
| `invariants`, `examples` | The invariants and recorded examples written to `penguin/invariants.json`. An example with a `sample` is generated by the builder |
| `features` | Each feature's `id`, `owner`, `title`, `role`, vendor, `area` (the scopes it declares when it opens), `start` (`base` or `main`) and `commits`. A feature with the role `migration` is the block Penguin opens from main for one owner's code on main, named as Penguin names it |
| `promotions` | Each time main moves to a feature's head: Lena's promotion stacking, Ines's expand, each block in turn, then Ines's contract |
| `split` | What Ines's agent declares with the expand: the seven rewrite rules and the six retiring contracts, each with its replacement |

Each commit names its `source` directory under `features/<feature id>/`, a `date`, a `message`, a
`tag` and an `author` (`owner`, `codemod` or a person). A migration or revision names its `fix`:
the scope, the kind (`migration` or `revision`) and the pytest node IDs it makes pass. A checkpoint
names in `fails_alone` the tests that fail on it alone. A commit with `"merge": "main"` merges main
into its branch first. Its parents are main and the branch head. Its tree is main's tree with
every file the branch's commits laid. Each reader's migration uses it, since the reader started from
`base` and the replacements are on main. A commit with `"onto": "main"` starts from main as it
stands, whose history holds the branch head. Ines's contract uses it.

Every id, path, contract, tag, test ID, name and email address is checked before anything is
written. Ids are lowercase words joined by `-`. Paths hold plain segments with no `..` and no
leading `/`. Names and email addresses hold no `<`, `>` or line break, because they go into commit
headers. `tests/test_money_fixture_builder.py` feeds hostile values such as `../money`,
`money; rm -rf /`, `/etc/` and `--force` to the loader.

## Branches and tags

`base` (tag) is the first commit. `main` starts there and moves in this order: Lena's promotion
stacking, Ines's expand, the nine blocks for code on main, then Ines's contract. Every other branch
is `feature-<id>`. Each commit carries the tag `feature-<id>-<tag>`.

| Role | Features | Start |

| Reader | 23 features in the nine scopes that call the float API, listed below | `base` |

| Late starter | `currency-filter` (Sun) | `main` after the expand |

Each reader's `checkpoint` adds one module that calls the float API, plus its test. Its `migrate`
commit, written by its builder, merges main and moves the module onto `Money`. The module's own
functions keep their types and results, so its test file is unchanged.

### Ines's split

| Tag suffix | Change |
|---|---|
| `checkpoint` | The expand. `shared/money/__init__.py` gains `Money` with `sum()`, `times()`, `scaled()`, `major()` and `display()`. `shared/money/discounts.py` gains `discounted()`. `orders/model.py` gains `line_total_minor()` and `order_total_minor()`. No existing function changes |
| `contract` | Starts from main as the last block left it. `price()`, `total()`, `display()`, `percent_off()`, `line_total()` and `order_total()` are removed with their own tests in `shared/money/tests` and `orders/tests/test_model.py` |

`Line.unit_price` and `CartLine.unit_price` stay floats: the dollar amount an order record stores.
The expand reads a stored price into the order's currency with `line_total_minor()`. No stored data
shape changes, so the stored data rule asks no scope for a marker.

## Expected failures and fixes

`pins.json` maps each test a migration or revision makes pass to that commit. The slow suite
(`tests/test_money_fixture_reproduction.py`) checks every row.

- **Every commit.** Each commit passes every scope's tests, except the tests it names in
  `fails_alone` and those a later commit of its feature fixes.
- **The yen.** `checkout/tests/test_japan.py::test_yen_charged_at_face_value` fails on the
  `japan-launch` checkpoint alone: float main charges 150 yen times two as 30000. The migration
  prices yen lines as `Money` in JPY, so the charge is 300.
- **The tax block.** On `whole-order` the two per-line tax tests fail: rounding the subtotal once
  turns 35 cents into 36 on a three-line order. `per-line` makes them pass.
- **Running features once the float API leaves main.** Merged with Ines's contract, each reader's
  checkpoint and Noor's second checkpoint fail their own tests. Merged with the contract, each
  migration passes.
- **Unaffected features, the late starter and Hugo's rounding mode.** Each passes merged with the
  split. Hugo's change sits in `shared/money/rounding.py`, which the expand does not touch.
- **The expand.** Its impact report lists only added symbols, with no changed signature, no removed
  export and no changed stored data shape.

## Invariants and the tax sample

`penguin/invariants.json` declares 18 invariants across the fourteen scopes that hold prices. Tax declares
"Tax is rounded per line item" (`tax-per-line`) and "Each order is taxed at its region's rate".
Analytics declares two protected invariants: "Daily revenue equals the sum of that day's order
totals" and "Revenue in different currencies is never added together".

Each test that `pins.json` lists under `fixes` has a one-line docstring stating what the test
protects. A merge plan states each break with that docstring. A test that checks a declared
invariant repeats the invariant's statement: `test_tax_rounded_per_line` reads "Tax is rounded per
line item." Every other test states its own rule in the same form, such as "A line's total is its
price times its quantity."

`tax/examples/invoice_tax.json` records 5,000 US orders for `tax/invoice.py::invoice_tax_minor`.
Each case passes the stored order record through `orders/model.py::Order.from_record`, so main and
the tax block compute the tax from the same stored record. The builder draws every order
from a fixed seed and keeps every draw: one to six lines, prices from 49 cents to $19.99,
quantities up to four, in one of four regions.

`examples/money-minor-units/reviews/` holds the two review forms Rahul's agent submits on the tax
block: one for the whole-order step (`tax-per-line` breaks) and one for the revision (both
invariants hold). Neither names a stored data marker. Tax only reads `orders.model.Line` and
`Order` and stores nothing derived from them. The split changes no stored shape: the expand's
impact report lists no stored data shape. Had the store's shape changed, the marker would belong on
Ines's change, which owns the store, under PRD section 6 item 5.

## Checking the case with the bridge

Build into a directory, then run the tax review on the whole-order step and on the revision, each
against main as the block found it:

```sh
penguin-bridge review --repo /tmp/larder \
  --base feature-migrate-rahul-money-minor-units-whole-order^ \
  --fork feature-migrate-rahul-money-minor-units-whole-order \
  --scope tax --form examples/money-minor-units/reviews/tax-whole-order.json
penguin-bridge review --repo /tmp/larder \
  --base feature-migrate-rahul-money-minor-units-whole-order^ \
  --fork feature-migrate-rahul-money-minor-units-per-line \
  --scope tax --form examples/money-minor-units/reviews/tax-per-line.json
```

The first run reports `invoice_tax_minor` differing on 1633 of 5000 inputs, by one or two cents. It
raises a broken `tax-per-line` invariant for Rahul. No single-line order differs:

| Lines in the order | 1 | 2 | 3 | 4 | 5 | 6 |
|---|---|---|---|---|---|---|
| Orders differing, whole-order step | 0 | 227 | 267 | 356 | 364 | 419 |
| Orders differing, per-line revision | 0 | 2 | 1 | 1 | 0 | 6 |

The second run reports 10 of 5000 differing by one cent each, with no exception. On each of the 10
orders one line's exact tax is a half cent, all in California at 7.25%. Main's floats compute that
tax as 0.4999… of a cent and round it down. The revision rounds the exact half up, as main's own
rounding mode (`ROUND_HALF_UP`) states. The revision's tax equals exact decimal arithmetic on all
5,000 orders, so the 10 differences are float drift on main.

## The split on the preview seed

`scripts/preview/seed.ts` runs the split on the fixture's data through the ProjectAgent's modules and
the check runner's programs. `apps/worker/test/money-split.test.ts`, `money-retiring.test.ts` and
`contract-sort-fixtures.test.ts` check each step below. A seed run without the originating agent's
`impact` and `check` took 336 seconds on a laptop running other test suites.

1. **Open.** Ines's feature declares money and orders. Four running features work there, so its
   start waits on Hugo (`rounding-mode`) and on Tomas (`reorder`, `split-shipments`,
   `substitutions`). Each approves.
2. **Expand.** Penguin sorts the first checkpoint's contract diff: 25 additive entries and nothing
   else, so the sort records no split and asks for no merge plan. The plan Ines's agent proposes
   there names no part. It declares the seven rules and the six contracts the expand replaces.
   Penguin checks each against main, the facts run's callers and the checkpoint, and records the
   split from the declaration under one signed `contract_split` record. Main moves to the expand,
   and the six contracts retire with their rules under one signed `retire_symbols` record.
3. **Count.** Penguin's count after the expand finds 84 callers of the float API: 39 on main and 45
   in the readers' own changes. A use in a retiring function's own module or its scope's tests is
   no caller, so the tests in `shared/money/tests` and `orders/tests/test_model.py` are counted as
   the contract's own uses.

   | Retiring contract | Replacement | Rules | Callers | On main |
   |---|---|---|---|---|
   | `shared/money/__init__.py::price` | `Money` | 4 | 16 | 4 |
   | `shared/money/__init__.py::total` | `Money.sum` | 1 | 13 | 6 |
   | `shared/money/__init__.py::display` | `Money.display` | 2 | 18 | 8 |
   | `shared/money/discounts.py::percent_off` | `discounted` | 0 | 2 | 2 |
   | `orders/model.py::line_total` | `line_total_minor` | 0 | 12 | 6 |
   | `orders/model.py::order_total` | `order_total_minor` | 0 | 23 | 13 |

4. **Migrate.** Penguin proposes one migration plan per owner group, ten in all:

   | Owner | Places | Uses |
   |---|---|---|
   | ade | `partial-refunds`, `store-credit`, scope `refunds` | 5 |
   | jun | `basket-size`, `cohort-ltv`, `store-league`, scope `analytics` | 12 |
   | kofi | `instant-payouts`, `weekly-statements`, scope `payouts` | 11 |
   | lena | scope `promotions` | 2 |
   | mei | `business-accounts`, `credit-notes`, `pdf-layout`, scope `invoicing` | 14 |
   | noor | `cart-sync`, `order-history`, scope `mobile-api` | 7 |
   | priya | `japan-launch`, `saved-carts`, `tip-jar`, scope `checkout` | 6 |
   | rahul | `bottle-deposit`, `tax-exempt`, scope `tax` | 4 |
   | sam | `order-shipped`, `refund-email`, `weekly-digest`, scope `messaging` | 15 |
   | tomas | `reorder`, `split-shipments`, `substitutions` | 8 |

   The declared rules rewrite every use in 10 of the 32 parts, so the check runner writes those and
   tries each on its trial tree with no review form. Kofi's `instant-payouts` passes and Penguin
   approves it. The other 9 fail their scope's tests there, so each becomes an edit task with the
   failing check attached. In `store-league`, for one, the `display` rule turns
   `money.display(amount)` into `amount.display()` while `amount` is still a float. Each of the other
   22 parts is an edit task from the start: a reader's own changes for its builder, code on main for
   the steward of the scope's DRI in the plan's block.
5. **Midway.** Noor's pagination reports its second checkpoint, whose own change calls
   `money.display(line_total(line))`. The retiring-calls check answers two next steps. Step 4 goes to
   `@noor/pagination` for `line_total`, which no rule covers. It names `line_total_minor`. Step 3
   goes to Penguin for `display`, which the `display` rule rewrites. The place joins Noor's open plan
   with 3 uses under one `migration_joined` record.
6. **Late starter.** Sun's `currency-filter` opens from main after the expand and uses `Money` from
   its first commit. No plan reaches it.
7. **Write.** Each reader's builder reports its migration as a checkpoint, the fixture's `migrate`
   commit, whichever writer Penguin named. Tomas's plan holds only running features, so it closes once
   their migrations are written. Each other owner's steward writes the block Penguin opened for that
   owner's code on main, in the order the table in
   [The blocks for code on main](#the-blocks-for-code-on-main) lists. Penguin lands each block once
   its parts are written. The check runner then checks and promotes it. After each promotion Penguin
   counts again: 36, 33, 25, 23, 15, 11, 5, 2 and 0 callers left. Rahul's agent reviews the tax block
   at each step. The whole-order step raises the broken `tax-per-line` invariant for Rahul. The
   per-line revision holds.
8. **Contract.** Each retiring contract with no caller left gets Penguin's contract step on Ines's
   feature, approved with no place: `price()` after Kofi's block, `total()` after Jun's,
   `line_total()` after Sam's, `order_total()` and `display()` after Noor's and `percent_off()` after
   Lena's. Ines's contract checkpoint removes all six with their own tests. Its facts run shows each
   removed, then the feature lands. Penguin closes the six retiring records under one
   `symbols_removed` record.

The run shows one limit of today's rules:

- **No protected-path confirmation.** Jun's own steward writes the analytics block, so the change to
  `analytics/revenue_report.py` is Jun's own and Jun is not asked to confirm it.

## Changing the fixture

A change to `larder.json` or to a source directory changes the SHA of every commit built after it.
Run `uv run pre-commit run --all-files` first, because ruff can rewrite a fixture source file. A new
top-level package goes into `known-first-party` in `examples/ruff.toml`, so ruff sorts its imports
as it would in the built repository. Then
run `python examples/money-minor-units/build.py <empty dir> --pins > examples/money-minor-units/pins.json`.
`tests/test_money_fixture_builder.py` fails until `pins.json` matches a fresh build. Run
`uv run detect-secrets scan --baseline .secrets.baseline` afterwards to record the new SHAs.
